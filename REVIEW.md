# REVIEW — часть 1, code review

Оба файла работают на маленьких данных, но в продакшене сломаются.
Ниже проблемы по убыванию опасности. В конце: что я исправил в коде
(файлы лежат в папке code-review рядом с оригиналами).

## TimesheetReportHandler.cs (отчёт стоимости по проектам)

1. **Вся коллекция загружается в память.**
   Фрагмент: `Find(FilterDefinition<TimeEntry>.Empty).ToListAsync()`,
   фильтр по месяцу делается потом через `Where` в C#.
   Чем грозит: записей табеля за годы работы могут быть миллионы.
   Отчёт съест память и уронит сервис по OutOfMemory или таймауту,
   заодно перегрузив базу.
   Как чинить: фильтр по диапазону дат передать прямо в запрос
   `Find(e => e.Date >= начало && e.Date < конец)`, а лучше считать весь
   отчёт агрегацией на стороне MongoDB.

2. **`.Result` внутри цикла.**
   Фрагмент: `...FirstOrDefaultAsync().Result`.
   Чем грозит: sync-over-async. Под нагрузкой пул потоков голодает,
   возможны дедлоки, API перестаёт отвечать. Плюс это медленно: каждый
   `.Result` блокирует поток.
   Как чинить: метод и так `async`, просто писать `await`.

3. **Неправильная ставка.**
   Фрагмент: `employee.Rates.FirstOrDefault().Value`.
   Чем грозит: берётся первая ставка в истории сотрудника, а не ставка,
   которая действовала на дату записи. Если ставки менялись, отчёт
   показывает неправильные деньги. Это самая дорогая ошибка из возможных:
   неверная отчётность для бухгалтерии.
   Как чинить: брать последнюю ставку, у которой `From <= даты записи`.

4. **N+1 запросов.**
   Фрагмент: запрос сотрудника на каждую запись, запрос проекта на каждый
   новый проект внутри цикла.
   Чем грозит: на 10 000 записей будет ~10 000 лишних запросов к базе,
   отчёт вместо миллисекунд будет думать секунды.
   Как чинить: загрузить сотрудников и проекты один раз списком и
   сложить в словари по id.

5. **Null из базы не проверяется.**
   Фрагмент: `employee.Rates...` и `project.Id` без проверки, что
   `FirstOrDefaultAsync` что-то вернул.
   Чем грозит: одна битая запись (сотрудник удалён) и весь отчёт падает
   с NullReferenceException, пользователь видит 500.
   Как чинить: проверять на null, записи без справочника пропускать.

6. **Деление на ноль.**
   Фрагмент: `row.Amount / row.Budget * 100`.
   Чем грозит: у проекта с бюджетом 0 получим 500 или NaN/Infinity
   в данных.
   Как чинить: проверять бюджет перед делением.

7. **`double` для денег.**
   Фрагмент: поля `Amount`, `Budget`, `Rate.Value` типа double.
   Чем грозит: копейки теряются, суммы «не сходятся на копейку»,
   сравнения денег через == работают через раз.
   Как чинить: decimal для всех денежных полей.

8. **CancellationToken не используется.**
   Фрагмент: параметр `token` принимается и нигде не передаётся.
   Чем грозит: тяжёлый отчёт нельзя отменить, запрос будет крутиться
   даже после ухода пользователя со страницы.
   Как чинить: передавать токен во все вызовы драйвера.

## TimeEntriesPage.tsx (экран «Табель»)

1. **Бесконечный цикл запросов.**
   Фрагмент: `useEffect(() => { load(); })` без массива зависимостей.
   `load()` обновляет состояние, состояние вызывает новый рендер,
   новый рендер снова вызывает эффект. Запросы летят без остановки,
   пока открыта страница.
   Чем грозит: сервер захлёбывается, интерфейс мигает, трафик уходит
   в никуда.
   Как чинить: `useEffect(() => { load(); }, [props.year, props.month])`.

2. **Мутация состояния.**
   Фрагмент: `entries.push(body); setEntries(entries);`
   Чем грозит: массив тот же, React может не перерисовать таблицу.
   Новая запись то появится, то нет. Плюс в список попадает объект без
   id и имён, строка отображается с пустыми ячейками.
   Как чинить: после сохранения перезагрузить список `await load()`.

3. **Дата зависит от локали браузера.**
   Фрагмент: `date: new Date(date).toLocaleDateString()`.
   Чем грозит: сервер получит «05.03.2026» или «3/5/2026» в зависимости
   от настроек машины, где-то дата уедет на день назад. Бэкенд такой
   формат не поймёт.
   Как чинить: отправлять строку в формате yyyy-MM-dd.

4. **Ошибки сети никто не обрабатывает.**
   Фрагмент: все `fetch(...)` без проверки `response.ok` и без catch.
   Чем грозит: при ошибке или 400 от сервера пользователь ничего не видит,
   запись «сохранилась», а на самом деле нет.
   Как чинить: проверять ответ и показывать сообщение пользователю.

5. **Мелкие, но настоящие проблемы.**
   `==` вместо `===`, `parseFloat` по полю, которое может быть числом,
   `key={index}` (при удалении строки React перепутает строки),
   `any[]` вместо типов, `alert` вместо нормального сообщения,
   `PUT` для создания записи, часы строкой без проверки.

## Что бы я поменял в структуре (а не в отдельных строках)

1. Отчёт должен считаться агрегацией в MongoDB: соединение со
   справочниками через $lookup, группировка по проекту, расчёт процентов.
   Обработчик тогда только возвращает готовые строки.
2. Прямые вызовы `_db.GetCollection("...")` с магическими строками
   разбросаны по коду. Нужен слой репозиториев или хотя бы константы
   с именами коллекций.
3. На фронте нет слоя работы с API: fetch размазан по компоненту,
   типы заменены на any. Я бы вынес функции запросов в отдельный модуль
   с типами и отдал состояние сервера react-query: кэш, повторный запрос
   после мутаций и обработка ошибок решаются им.
4. Обработка ошибок должна быть частью дизайна с самого начала
   (глобальный обработчик на бэке, показ ошибок на фронте), а не
   «добавим потом».

## Что я исправил в коде

По заданию нужно исправить одну-две самые важные проблемы.

1. `code-review/TimesheetReportHandler.fixed.cs` — исправлены №1 (вся
   коллекция в память) и №3 (неправильная ставка), это самые опасные.
   При переписывании метода заодно ушли №2 (.Result), №4 (N+1), №5 и №6
   (проверки на null и нулевой бюджет), потому что иначе метод остался бы
   сломанным в других местах. №7 (double для денег) и №8 (токен)
   сознательно не трогал, чтобы правки были минимальными.
2. `code-review/TimeEntriesPage.fixed.tsx` — исправлены №1 (бесконечный
   цикл запросов) и №2 (мутация состояния). Остальное не трогал.
